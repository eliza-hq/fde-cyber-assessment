# Experimental runtime attempt — not a candidate target

This is an incomplete, unverified diagnostic attempt from 2026-11-12. Do not distribute or run as an assessment. It does not pin Python dependencies, does not supply fixtures, and has not created a site or verified access, reset, teardown or isolation. The Compose configuration is a proposed first test, not a tested lifecycle.

The Dockerfile expected two local Git clones in its build context: `erpnext` at `5a86717902e25a07e7cb1923fb84ca552fd687ee` from the assessment repository, and `frappe` at `235043604dc97304b5517c77e744273eb035d904` with a local branch named `assessment`. The latter was the upstream Frappe `develop` head observed during this attempt, selected because the target requires Frappe 17 and its CI follows `develop`; compatibility has not been established. The target requires Python >=3.14. The pinned CI base has Python 3.14.6, Node 24.17.0, MariaDB 11.8.9, Redis 7.0.15 and Bench 5.31.0; the host is arm64 and the image is amd64, so the build used emulation. Its default `python3` is 3.12.3, hence the explicit Python path.

`docker build --platform linux/amd64` initialized the Frappe bench and installed the ERPNext Python package. The ERPNext banking Yarn install completed, but the nested islands Yarn fetch repeatedly reported `There appears to be trouble with your network connection. Retrying...`. The build was interrupted after repeated retries; no image was completed, and asset build and site creation were not reached. An HTTP request to the registry root from the host returned 200, which does not establish availability of the specific package or the container's network path. The proposed Compose project was never started; no assessment containers, networks or volumes were created. Pre-existing Docker resources were not modified. A CI base image and Docker build cache were added locally.

Before this approach can be used, resolve the package fetch, lock and verify all deployment dependencies and source revisions, build assets, create synthetic data, and independently verify startup, access, isolation, reset and teardown on a clean environment. The current release remains blocked.

### Runtime checks and remaining limits

The experimental site was created twice with the recorded revisions. The first configured host mapping did not work: `bench serve` initially bound container loopback, and Docker Desktop did not publish the requested port for an internal-only network. The Compose file now binds the service on the container interface and uses a small fixed-destination TCP relay on an additional ingress network. The app, database and Redis remain only on the internal target network; the relay is attached to both networks and publishes `127.0.0.1:18880`. This relay is experimental and has not received a security review. The application's outbound TCP connection attempt to `1.1.1.1:443` failed, a limited test rather than proof of complete isolation.

Through the relay, the login page returned HTTP 200 and the disposable `Administrator` account authenticated. `bench --site frontend list-apps` reported Frappe `17.0.0-dev` and ERPNext `17.x.x-develop (5a86717)`; the installed Git HEADs match the two revisions above. The ERPNext `islands/yarn.lock` was modified by the non-frozen install, adding dependencies; its diff and the observed Python package list are captured in `installed-islands-yarn-lock.diff` and `installed-versions.txt`. This is evidence of what this image installed, not a dependency lock or a reproducible build.

A project-scoped `down -v` followed by `up -d` removed a test file, Redis key, and test database. The replacement site initialized and the disposable Administrator login succeeded again. Final `down -v` removed the project's containers and networks; the port refused connections, and the host had the same count of 10 Docker volumes as before the test. This was not a clean-machine or independent test and does not establish all lifecycle cases: in particular, the current startup command always creates a site and ordinary container restart/recreation against retained state has not been validated. No synthetic exercise fixtures were supplied. The diagnostic image and build cache remain locally; pre-existing Docker resources were not intentionally removed. Release remains blocked.
